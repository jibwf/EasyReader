# E-link 墨水屏客户端计划

更新时间：2026-06-11

## 产品定位

`e-link-client` 不是服务端管理界面的缩小版，而是 EasyReader 在墨水屏设备上的专用阅读终端。它的第一目标是稳定、低干扰、可离线地阅读；同步、书架刷新、字体下载等联网能力都只能服务于阅读主线，不能反过来牵着阅读体验走。

从全局看，系统应该分成两层：

- 服务端是内容与同步中心，负责书源能力、书架主数据和跨设备共享状态。
- 客户端是设备侧阅读运行时，负责本地阅读、本地缓存、设备交互和低功耗 UI。

## 核心目标

- 阅读优先：任何设计都先保证“打开就能继续读”，再考虑联网功能。
- 本地优先：已缓存内容必须在断网或 WiFi 关闭时稳定可读。
- 同步收敛：同步只解决“跨设备继续读到哪”，不追求复杂实时镜像。
- UI 静态：不依赖动画、进度条和高频刷新，适配低性能 CPU、低内存和墨水屏刷新约束。
- 边界清晰：服务端不做设备 UI，客户端不做书源解析。

## 当前基线

- 客户端已经切换到章节阅读模型，不再计算或展示整书页码。
- 所有联网行为都应经过 WiFi 闸门，WiFi 关闭时禁止隐式联网。
- 已有本地章节缓存、进度同步、WiFi 恢复后延迟同步和离线缓存任务的实现基础。
- 当前实现已经具备“阅读优先”的雏形，但计划文档需要从“网络整改说明”升级为“完整客户端方案”。

## 与当前服务端契约对齐

当前服务端不是抽象意义上的“未来同步中心”，而是已经有一套明确字段的现有 API。墨水屏端应该直接按这套基线对接，而不是自己再发明一套新模型。

当前必须对齐的事实：

- 共享阅读进度键不是 `bookId`，而是 `user_id + book_url`，同时携带 `source_url`。
- 共享进度字段当前是 `book_url`、`source_url`、`book_name`、`chapter_idx`、`chapter_title`、`chapter_url`、`position`、`device_id`、`revision`、`updated_at`。
- 当前没有统一账号系统，`user_id` 与 `device_id` 仍由客户端自己生成和持久化。
- `/api/offline/tasks` 当前是同步执行并返回结果的任务风格接口，不应按“完整后台任务队列”设计客户端。
- 服务端已经支持通过响应头暴露 `X-Server-Version`、`X-API-Contract-Version` 和支持的客户端类型。

墨水屏端请求头建议固定带上：

- `X-Client-Type: eink-android`
- `X-Client-Version: <客户端版本>`
- `X-API-Contract-Version: 2026-06-11`

## 客户端主线

### 阅读闭环

- 进入书籍后优先打开本地目录和本地章节正文。
- 未缓存章节只显示静态提示和明确入口，不在阅读路径里偷偷拉远端内容。
- 阅读器核心动作是继续阅读、上一章/下一章、目录跳转、返回书架，而不是整书分页系统。

### 进度闭环

- 设备内保存细粒度阅读状态：当前书、当前章、滚动锚点或段落位置、最近打开时间。
- 跨设备只同步粗粒度进度：当前书、当前章、更新时间、设备标识。
- WiFi 不可用时只在本地记录；WiFi 恢复后再补交待同步进度。
- 待同步队列按“每本书只保留最后一条有效进度”收敛，不保留同一本书的历史章节轨迹。

### 设备闭环

- 阅读设置必须本地即时生效：字体、字号、行距、边距、刷新模式、按键映射。
- UI 反馈以静态文本和简单状态为主，不依赖动画或频繁重绘。
- 低电量、低内存、弱 WiFi 场景下优先保证“能继续读”，而不是“所有功能都在线”。

## 服务端与客户端处理边界

| 领域 | 服务端负责 | 客户端负责 |
| --- | --- | --- |
| 书源接入与解析 | 搜索、详情抓取、目录解析、正文抓取、数据清洗 | 不直接接书源，不解析网页规则 |
| 书架主数据 | 用户书架、分类、服务端缓存统计、云端书籍元数据 | 本地展示、排序、筛选、最近阅读入口 |
| 章节内容 | 提供规范化目录与章节内容接口，按需准备缓存 | 本地缓存、章节加载、未缓存提示、缓存状态展示 |
| 阅读进度 | 存储跨设备共享的粗粒度进度与更新时间 | 保存本地细粒度位置、待同步队列、冲突提示 |
| 字体与资源 | 提供字体清单、下载地址、版本信息 | 下载、启用、回退、清理本地字体 |
| 同步策略 | 接收和返回进度、书架和基础元数据 | 决定何时同步、何时排队、何时提示用户 |
| UI 与设备适配 | 不感知墨水屏刷新和交互细节 | 阅读排版、刷新模式、实体按键、触控热区、无动画策略 |

边界原则：

- 服务端输出稳定、规范化的数据，不承担设备 UI 状态。
- 客户端输出可预测的阅读体验，不承担书源解析和复杂内容清洗。
- 服务端是内容与同步中心，不是阅读器渲染器；客户端是阅读器，不是缩小版管理后台。

## 同步策略

同步内容只保留两类：

- 轻量同步：阅读进度、书架基础元数据、字体清单、缓存状态摘要。
- 显式下载：章节离线缓存、字体文件、手动刷新书架或目录。

同步原则：

- 阅读过程中默认只同步进度，不做章节正文隐式联网。
- WiFi 开启 5 秒后做一次轻量全量同步；如果等待中或同步中 WiFi 关闭，直接取消。
- 章节切换、退出阅读、手动同步时可以上报进度；WiFi 不可用时进入待同步队列。
- 章节正文下载永远是显式动作，不归入自动同步。
- 不追求秒级实时双向同步，优先保证低功耗、低复杂度和可恢复性。

待同步队列规则：

- 队列键建议按 `user_id + book_url + source_url` 去重。
- 同一本书只保留最后一次阅读位置，不保留“第 2 章、第 3 章、第 4 章、第 5 章”这类连续历史进度。
- 例如用户已经读到第 5 章，待同步队列里应只剩“第 5 章的最后位置”，前面章节的待同步项直接被覆盖。
- 这样做的目的不是省几条记录，而是确保服务端接收到的是“当前应恢复到哪里”，而不是一串已经过时的中间状态。

进度模型应拆成“本地模型”和“上行服务端模型”：

- 客户端本地：`book_url + source_url + chapter_idx + anchor/offset + updated_at`
- 服务端上行：`user_id + device_id + book_url + source_url + book_name + chapter_idx + chapter_title + chapter_url + position`
- 服务端回包：在上行字段基础上增加 `revision`、`updated_at`、`accepted`、`conflict`、`conflict_reason`

映射规则：

- 墨水屏端本地可以保存比服务端更细粒度的位置，例如滚动锚点、分页内偏移、最后阅读时间。
- 上报到服务端时只保留服务端当前能接收的 `position: float`。
- 如果墨水屏端使用纯章节模型，首版可以把章节内位置固定为 `0.0`，后续再按需要映射为百分比。
- 服务端返回冲突时，客户端不应该直接覆盖本地状态，而应该进入显式冲突处理或等待用户确认。
- 待同步队列里的旧进度在同一本书内应被新进度覆盖，避免恢复网络后把一串过时章节位置重新顺序上报。

当前最小对接接口：

- `/api/version`
- `/api/books`
- `/api/content/chapters`
- `/api/content/chapter`
- `/api/sync/progress/upsert`
- `/api/sync/progress/pull`
- `/api/offline/tasks`
- `/api/offline/catalog`
- `/api/fonts`
- `/api/fonts/{font_file_name}/download`

## UI 方向

### 阅读页

- 默认全屏正文，突出书名、章节标题和少量必要状态。
- 不显示整书页码，不做整书分页，不为了页码去后台计算未缓存章节。
- 支持目录跳转、上一章/下一章、继续阅读、未缓存提示和离线缓存入口。

### 书架页

- 重点展示最近阅读、当前离线可读、同步状态和未同步标记。
- 书架是阅读入口，不是复杂管理台；复杂服务器操作收进二级界面。

### 设置与状态

- 设置页只保留与阅读直接相关的配置：字体、字号、刷新模式、同步模式、WiFi 在线状态。
- 网络状态展示要弱提示、可理解，不用进度条轰炸用户。
- 所有可联网操作在 WiFi 不可用时直接禁用或给出短文案说明，不让用户点了再失败。

## 近期功能重点

### 阅读闭环补齐

- 继续阅读入口稳定化。
- 未缓存章节静态提示与一键离线缓存。
- 目录跳转、最近章节和阅读历史。
- 自动翻页：按阅读页本地排版结果计时翻页，支持暂停、继续和实体按键控制。

### 进度同步补齐

- 本地待同步队列，且按每本书只保留最后一条进度去重。
- 客户端与服务端进度冲突处理。
- 章节切换与退出阅读时的低频同步。

### UI 收敛

- 统一静态状态反馈。
- 阅读页菜单和设置面板去动画。
- 书架聚焦最近阅读、离线状态和同步状态。

### 设备适配

- 实体按键映射。
- 墨水屏刷新模式切换。
- 低 RAM 和弱 CPU 下的缓存与渲染降载。
- 自动翻页时的局部刷新策略，避免频繁全刷。

### 有声书最小对接

- 只接服务端音频任务和已生成音频，不在客户端做文本切句、TTS 合成和音频缓存策略。
- 第一版只做播放、暂停、章节切换和进度记忆，不做复杂播放器 UI。

## 中期功能规划

- 书签、批注、摘录，先本地优先，再决定是否同步。
- 书内搜索、章节收藏、目录过滤。
- 按书维度的离线缓存策略，例如“缓存后 N 章”或“仅缓存当前书”。
- 多设备阅读提示，例如“服务器上有更新进度，是否跳转”。
- 本地导入能力与服务端书架的协同策略。
- 搜索结果页只消费服务端优化后的搜索结果，不在墨水屏端实现书源搜索规则解析。

## 暂不优先

- 客户端直接做书源搜索规则解析。
- 客户端整书分页和复杂页码系统。
- 重型动画、复杂看板式同步页面和持续后台轮询。
- 把客户端做成服务端管理后台的完整镜像。
- 在墨水屏端实现完整有声书生成链路。

## 当前工程验证

当前工程已具备的基线：

- 本地章节阅读优先。
- WiFi 闸门控制联网。
- 离线缓存任务可控。
- 5 秒延迟同步机制已进入现有设计。

已验证命令：

```bash
cd e-link-client
JAVA_HOME="/Applications/Android Studio.app/Contents/jbr/Contents/Home" ./gradlew :app:testDebugUnitTest :app:assembleDebug --no-daemon
JAVA_HOME="/Applications/Android Studio.app/Contents/jbr/Contents/Home" ./gradlew :app:assembleRelease --no-daemon
```

验证结果：命令通过，当前主要剩 Android Gradle Plugin 对 compileSdk 35 的兼容性警告，以及 release strip 原生库的非阻塞提示。

## 下一步落地建议

1. 先按当前服务端字段把进度、离线任务和字体接口接通，不再抽象出第二套并行契约。
2. 再按阅读闭环整理 UI，把书架、阅读页、目录和离线缓存入口四个核心界面先稳定。
3. 最后补设备向能力：实体按键、刷新模式、低内存策略和仪器测试。
